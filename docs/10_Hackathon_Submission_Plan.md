## 3. Benchmark: Decider vs Bedrock judge (bonus points)

Goal: show measured latency and cost for the same guardrail question, honestly.

**Task:** scenario grounding (`noul`): "Does this scenario's prose/Gherkin assert the same outcome as its structured oracle and rule?"

**Dataset (`bench/grounding_set.jsonl`, ~40 items):** for each of S01–S05, 4 correct paraphrases + 4 mutated versions (e.g. "two ledger postings" in S04, wrong amount 125.00 in S01, "mark payment failed" after timeout in S02, missing "status verified before retry" in S05). Labels come from the fixed catalog in [07](07_Test_Automation_Design.md) §6, written by the Test SME, not generated by a model. Synthetic data only.

**Runs (`bench/run_bench.py`):**
1. Decider on EC2 T4 GPU (and local CPU for reference).
2. A small Bedrock model as judge (e.g. a Claude Haiku-class model; use whichever model ID is enabled in your account) with a yes/no prompt.
3. Hybrid: Decider when confidence ≥ τ, else Bedrock.

**Report (table in article and repo README):** accuracy vs labels, p50/p95 latency, cost per 1,000 decisions (Bedrock: tokens × list price; Decider: instance $/hr ÷ measured throughput), and % escalated in the hybrid. State the dataset size and that results are indicative only. If Bedrock is more accurate, say so — the hybrid row is the story.

3. **The decision pattern** (`#guardrails`): confidence-gated guardrail as an `InterventionHandler`; code snippet (~20 lines) from `decider_gate/`.
4. **Demo walkthrough**: seeded S04 gap (stated openly) → grounding + REMEDIATE_GAP → 5/5 → Approve → Execute → T04 fails: expected 1 ledger posting, got 2 → "Agent workflow COMPLETED, payment verification FAILED".
5. **Numbers**: the benchmark table.
6. **What I learned / limits**: where Decider was confident and right, where it wasn't, the CPU-fallback gotcha, why the human gate stays.
7. **Try it**: repo link, `decider_gate` quickstart.
